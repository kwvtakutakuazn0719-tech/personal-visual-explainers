# スキル作成指示書: `post-review-save`

## 目的

設計レビューサイクル（複数の専門レビューを順番に実施して設計を磨くワークフロー）が完了した後、
その成果物を git にコミットして記録を残すためのグローバルスキル。

どのプロジェクト・どのリポジトリで設計レビューを行った後でも使えるように、
グローバルスキルとして作成する。

---

## 作成場所

```
C:\Users\party\.cursor\skills-cursor\post-review-save\SKILL.md
```

参照先の rubric ファイルは不要。SKILL.md 1ファイルだけで完結させる。

---

## トリガー条件（ユーザーがこう言ったら起動する）

- 「レビュー後保存して」
- 「設計保存して」
- 「コミットして」
- 「保存コミットして」
- 「post-review-save」

---

## スキルがやること（ワークフロー）

### Step 1: プランファイルを特定する

`C:\Users\party\.cursor\plans\` フォルダを確認し、対象のプランファイル（`.plan.md`）を特定する。

- 1ファイルしかなければそれを対象にする
- 複数ある場合は「どれを保存しますか？」とファイル名一覧を提示してユーザーに選ばせる
- 0ファイルの場合は「保存対象のプランファイルが見つかりません」と報告して終了

### Step 2: 保存先フォルダを確認・作成する

現在の git リポジトリのルートに `docs/design/` フォルダが存在するか確認する。

- 存在しなければ作成する
- 存在すれば何もしない

### Step 3: プランファイルをコピーする

プランファイルを `docs/design/` にコピーする。

- ファイル名はプランファイルの元のファイル名をそのまま使う
- 既に同名ファイルが存在する場合は上書き（更新）する

### Step 4: git status を確認する

`git status` を実行し、変更されているファイルの一覧を取得する。

- 変更がない場合（コミット済み）は「保存済みです。新しい変更はありませんでした。」と報告して終了

### Step 5: git add する

以下をステージングする。

```
git add docs/design/
git add .claude/skills/      ← スキルファイルの変更があれば
git add .cursor/rules/       ← ルールファイルの変更があれば
```

他の変更ファイルについては、ユーザーに「このファイルも含めますか？」と確認せず、
スキル・ルール・docs 以外の変更は含めない（アプリコードの変更は別途ユーザーが管理する）。

### Step 6: コミットメッセージを生成してコミットする

以下の形式でコミットメッセージを生成する。

```
docs: レビューサイクル完了・設計保存 [{プランファイル名から .plan.md を除いた名前}]

- プランファイルを docs/design/ に保存
- レビュー件数: {コミットに含まれる変更ファイル数} 件の変更を記録
```

`git commit` を実行する。

### Step 7: 完了報告する

以下の情報をユーザーに報告する。

- コミットしたファイル一覧
- コミットメッセージ
- 「git push はまだ実行していません。push する場合は別途指示してください。」

---

## やらないこと（禁止事項）

- `git push` は明示的に「pushして」と言われない限り実行しない
- `git add .`（全ファイル一括add）は実行しない
- アプリケーションコード（`src/`, `apps/` 配下など）を勝手にコミットしない
- プランファイルを削除・移動しない（コピーのみ）
- コミットメッセージを勝手に変更しない（ユーザーが別のメッセージを指定した場合はそちらを優先）

---

## エラーハンドリング

| 状況 | 対応 |
|---|---|
| gitリポジトリ外で実行された | 「gitリポジトリ内で実行してください」と報告して終了 |
| プランファイルが0件 | 「保存対象のプランファイルが見つかりません」と報告して終了 |
| プランファイルが複数 | ファイル名一覧を提示してユーザーに選ばせる |
| git commit が失敗 | エラーメッセージをそのまま表示して「手動で確認してください」と伝える |

---

## 参考：このスキルが想定する利用シーン

1. ユーザーが設計プランを作り、5つの専門レビュー（業務・DDD・アーキテクチャ・運用・最終統合）を順番に実施する
2. 全レビューが終わり、プランが「実装に進んでよい」状態になる
3. **このスキルを呼び出す** → プランと変更済みスキルが git にコミットされる
4. ユーザーは新しいリポジトリ・新しいチャットで実装を開始する

このスキルは「設計フェーズの終わりに押す保存ボタン」の役割を果たす。
